# Runbook: резервные копии и восстановление PostgreSQL

Копии делает pgBackRest (спецификация [4.16](../backend-v2-spec.md), «Резервные копии»; решение A23). В S4 они уходят в локальный S3 на SeaweedFS (bucket `pgbackrest`); в S21 меняется только адрес хранилища (S3 российского провайдера) и сертификат. Цели: **RPO ≤ 5 минут** (WAL уходит в хранилище не реже раза в минуту), **RTO ≤ 1 часа** (учение на стенде укладывается в десятки секунд при пустой базе).

## Как это устроено

| Часть | Где | Что делает |
|---|---|---|
| `archive_command` | контейнер `postgres` | `pgbackrest archive-push` отправляет каждый заполненный сегмент WAL; `archive_timeout=60` закрывает сегмент раз в минуту, если база пишется |
| планировщик | контейнер `pgbackrest` ([deploy/backup/run.sh](../../deploy/backup/run.sh)) | при старте создаёт stanza, проверяет архивацию и делает первую полную копию; дальше раз в сутки в `BACKUP_AT` (03:00 UTC): **полная в воскресенье, в остальные дни дифференциальная** |
| хранилище | SeaweedFS, bucket `pgbackrest`, HTTPS-порт 8334 | pgBackRest ходит в S3 только по TLS; на стенде сертификат самоподписанный (в томе `s3ca` только сертификат, ключ лежит в `s3tls` и виден одному SeaweedFS) |
| шифрование | на стороне клиента, `aes-256-cbc` | ключ в секрете `deploy/secrets/pgbackrest_cipher_pass`, хранится отдельно от копий |
| хранение | 14 дней | `repo1-retention-full-type=time`, `repo1-retention-full=14`; старые копии и WAL стирает `expire` после каждой копии |
| настройки | [deploy/backup/pgbackrest.conf](../../deploy/backup/pgbackrest.conf) | ключи S3 и пароль шифрования приходят переменными окружения из секретов (у pgBackRest нет `*_FILE`) |

⚠️ **Потеряв `pgbackrest_cipher_pass`, вы теряете все копии**: без ключа их не прочитать. Храните его отдельно (менеджер паролей), а не только в `deploy/secrets`.

Не копируются: Redis (состояние восстанавливается из PostgreSQL, потеря очереди arq допустима), Kafka (появится в S9, тоже восстанавливается из outbox) и SeaweedFS (файлы; ночной `rclone sync` придёт в S21).

## Состояние копий

```bash
make backup-status       # или ./dev.ps1 backup-status
```

Печатает `pgbackrest info` (копии, диапазон WAL, размеры) и возраст последней копии. Код возврата 1, если копий нет или последняя старше 26 часов (порог оповещения из 4.15; тот же скрипт стоит в healthcheck контейнера `pgbackrest`). Что делать при тревоге:

1. `make logs-prod-like s=pgbackrest`: видно, на каком шаге остановился планировщик (он повторяет неудачную копию каждые 10 минут).
2. `docker compose -p messunjerr-stand -f deploy/compose.yml exec pgbackrest sh -c '. /backup/lib.sh && pgbackrest check'`: проверка конфигурации и архивации WAL.
3. Типичные причины: SeaweedFS не отвечает (`make ps-prod-like`), закончилось место, поменялся сертификат хранилища.

Копия по требованию (перед рискованной миграцией, перед обновлением):

```bash
make backup TYPE=full    # или diff, incr
```

## Недоступное хранилище копий

Если SeaweedFS (на сервере S3 провайдера) недоступен, PostgreSQL продолжает работать и принимать запись: `archive_command` падает с кодом 103, PostgreSQL пишет в журнал `archiving write-ahead log file … failed too many times, will try again later` и копит сегменты WAL в `pg_wal` (очередь `archive_status/*.ready`, по 16 МБ). Пока очередь не разобрана, **RPO растёт**, а `pg_wal` занимает диск; `archive-push-queue-max=1GiB` не даёт ему переполниться ценой пропуска WAL (после пропуска в архиве дыра, и нужна новая полная копия: `make backup TYPE=full`). Когда хранилище вернулось, очередь разбирается сама, за секунды.

Проверено на стенде (S4): хранилище остановлено на несколько минут, записано шесть сегментов, контейнер `postgres` пересоздан при непустой очереди. PostgreSQL не перезапускался, запись продолжалась, ничего не потеряно (сегмент остаётся в `pg_wal` на томе, пока `archive_command` не вернул успех, а каталог `spool-path` pgBackRest хранит только служебные статусы), после возвращения хранилища `pgbackrest check` и учение по восстановлению прошли. Опыт держится на `init: true` у сервиса `postgres` (строка в таблице ниже): не убирайте.

## Учение: восстановление на отдельной БД

```bash
make restore-drill       # или ./dev.ps1 restore-drill
```

Боевая БД и репозиторий копий не затрагиваются. Что делает [deploy/restore-drill.sh](../../deploy/restore-drill.sh):

1. пишет в боевую базу `backup_drill` метку **после** последней копии: она может попасть в восстановленную БД только из WAL;
2. запоминает ревизию миграций и число строк во всех таблицах приложения;
3. `pgbackrest check` переключает WAL и ждёт, пока сегмент с меткой уйдёт в хранилище;
4. контейнер `restore-drill` восстанавливает копию в свободный том `pgrestore`, поднимает кластер на порту 5433 **с выключенной архивацией**, доигрывает WAL и сверяет: метка найдена, ревизия миграций и число строк совпадают с боевой БД, контрольные суммы страниц включены;
5. печатает время восстановления файлов и доигрывания WAL (RTO) и итог `УЧЕНИЕ ПРОЙДЕНО` либо код возврата 1.

Почему архивация выключена: после восстановления кластер начинает новую ветку времени, и, если бы он продолжил отправлять WAL в тот же репозиторий, он испортил бы боевую историю.

Проводите учение после любых изменений схемы копий, после обновления PostgreSQL и раз в квартал (⚖️ цель 7 из спецификации).

## Боевое восстановление

Когда нужно: потеряна или повреждена база. Сервис недоступен всё время восстановления, поэтому порядок такой.

1. Остановить приём трафика и фоновые процессы, чтобы они не писали в базу: `docker compose … stop caddy api-a api-b worker worker-default` (на сервере, S21: тот же compose-файл).
2. Остановить `postgres` и `pgbackrest`.
3. Освободить каталог данных: **не удаляйте том**, пока не убедились, что копия читается. Надёжнее восстановить в новый том (`pgdata-restore`), проверить и переключить сервис на него.
4. Восстановить (в одноразовом контейнере с тем же образом, секретами и томом `s3ca`, как делает `restore-drill`):
   - до конца архива WAL (потеря не больше RPO): `pgbackrest --stanza=messunjerr --pg1-path=/var/lib/postgresql/18/docker restore`;
   - до момента времени (например, до ошибочного `DELETE`): `pgbackrest … restore --type=time --target="2026-10-07 09:15:00+00" --target-action=promote`;
   - конкретную копию: `--set=20261006-214641F`.
5. Запустить `postgres` с обычными настройками (`archive_mode=on`): новая ветка времени продолжит архив в тот же stanza. Сразу после запуска сделать полную копию: `make backup TYPE=full`.
6. ⚖️ **Выполнить `cli erasure-reapply`** до открытия сервиса: копии хранят данные уже удалённых людей до 14 дней, и восстановленная БД должна повторно уничтожить данные всех, кто есть во внешнем журнале уничтожения (4.16, 4.19). Команды пока нет: она придёт вместе с внешним журналом уничтожения (B-04 бэклога плана); до этого на рабочих данных людей восстановление проводить нельзя, на стенде с синтетическими данными можно.
7. Поднять миграции (`migrate`), приложение и Caddy; выполнить `make smoke`.

## Частые ошибки pgBackRest

| Сообщение | Причина и решение |
|---|---|
| `backup and archive info files exist but do not match the database` | stanza создана для другой базы (том PostgreSQL пересоздали, репозиторий остался). Если старые копии не нужны: очистить bucket `pgbackrest` (`make reset-prod-like` на стенде); иначе `stanza-upgrade`, если это обновление PostgreSQL |
| `unable to find primary cluster` при `stanza-create` | PostgreSQL ещё стартует (официальный образ сначала запускает временный сервер): подождать, планировщик повторит |
| `archive_command` падает, `pg_wal` растёт | хранилище недоступно (раздел выше); `archive-push-queue-max=1GiB` не даёт диску переполниться ценой пропуска WAL, поэтому недоступность дольше нескольких минут считается инцидентом: проверить SeaweedFS и сертификат |
| `untracked child process exited with exit code 103`, PostgreSQL перезапускает все серверные процессы, цикл восстановления | PostgreSQL оказался PID 1 и принял осиротевший процесс асинхронной архивации (`archive-async=y`) за свой дочерний; при недоступном хранилище (код выхода 103) он перезапускал все серверные процессы и обрывал соединения. В compose у `postgres` стоит `init: true` (PID 1 это tini): не убирайте |
| `[500] Internal Server Error` от хранилища | у SeaweedFS нет свободных томов для bucket (в логах `No writable volumes`); не задавайте `-volume.max` вручную, по умолчанию их число считается по месту на диске |
| `unknown group 'root' in backup manifest mapped to current group` | предупреждение при восстановлении не от root, безвредно |

## Ключи и ротация

- Ключи S3 копий (`s3_backup_access_key`, `s3_backup_secret_key`) принадлежат отдельному удостоверению `backup` в SeaweedFS: оно видит только bucket `pgbackrest`, а ключи приложения только `media`.
- Сменить ключи S3: создать новые секреты, перезапустить `seaweedfs`, `postgres` (читает при старте) и `pgbackrest`.
- Сменить пароль шифрования pgBackRest на лету нельзя: создаётся новый репозиторий (новый `repo1-path` и пароль), делается полная копия, старый хранится до истечения 14 дней.
