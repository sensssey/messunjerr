# Runbook: prod-подобный стенд

Стенд (спринт S4) повторяет боевой контур на ноутбуке: Caddy с TLS, две реплики API, воркеры, PostgreSQL 18 с pgBackRest, Redis, SeaweedFS, Mailpit; лимиты памяти и ядер как у VPS на 8 ГБ и 4 vCPU. Он живёт в отдельном проекте Compose `messunjerr-stand` со своими томами и портами, поэтому среду разработки (`compose.dev.yml`) не трогает: оба стека можно держать одновременно.

Спецификация: [4.16](../backend-v2-spec.md), [6.2](../backend-v2-spec.md). Журнал решений и результаты спайков: итоги S4 в [плане спринтов](../backend-v2-sprints.md).

## Запуск и остановка

```bash
make up-prod-like        # или ./dev.ps1 up-prod-like
```

Команда создаёт секреты (`deploy/secrets/`, один раз), собирает образы, поднимает сервисы и выгружает корневой сертификат Caddy в `deploy/.stand/root.crt`. Первый запуск занимает несколько минут (сборка образов), повторные около минуты.

| Адрес | Что там |
|---|---|
| https://messunjerr.localhost/api/v1/meta | API через Caddy (то же, что увидит браузер) |
| https://messunjerr.localhost/api/v1/docs | Swagger UI (стенд работает как `APP_ENV=stage`, в проде документации нет) |
| https://messunjerr.localhost/spike.html | ручная проверка SSE, WebSocket и presigned URL в браузере |
| http://localhost:8026 | Mailpit стенда (письма воркера) |

Порты публикуют только Caddy (80, 443 TCP и UDP для HTTP/3) и веб-интерфейс Mailpit (8026), оба только на `127.0.0.1`; остальное доступно лишь внутри сетей Compose. `*.localhost` браузеры и современный `curl` сами ведут на `127.0.0.1`; если ваш клиент не умеет, добавьте `127.0.0.1 messunjerr.localhost` в файл hosts.

```bash
make down-prod-like      # остановить, данные сохраняются
make reset-prod-like     # остановить и удалить тома стенда (dev-стек не затрагивается)
make ps-prod-like        # состояние сервисов
make logs-prod-like s=caddy
```

⚠️ Всегда запускайте стенд этими командами (или с `-p messunjerr-stand`): имя проекта задаётся явно, чтобы оно не совпало с проектом dev-стека (`messunjerr-v2`) и стенд не подхватил его тома.

## Корневой сертификат Caddy

Сертификаты выпускает внутренний центр Caddy (`tls internal`), его корневой сертификат браузеры не знают. Без доверия браузер покажет предупреждение, а `curl` откажется работать без `--cacert`. Доверять сертификату нужно один раз, и это решение ваше: скрипты ничего в систему не устанавливают.

```bash
make stand-ca            # выгружает deploy/.stand/root.crt и печатает команды
```

- Windows (Chrome, Edge, Яндекс.Браузер): `certutil -addstore -user Root deploy\.stand\root.crt`.
- Firefox: Настройки → Приватность и защита → Сертификаты → Просмотр сертификатов → Центры сертификации → Импортировать.
- Убрать доверие: `certmgr.msc` → Доверенные корневые центры сертификации → «Caddy Local Authority».

Сертификат лежит в томе `caddy_data`: пока том жив, он не меняется. После `reset-prod-like` создаётся новый, и доверие придётся выдать заново.

`curl` без изменения системы: `curl --cacert deploy/.stand/root.crt https://messunjerr.localhost/api/v1/meta`.

## Что где работает

| Сервис | Лимит | Назначение |
|---|---:|---|
| `caddy` | 128 МБ | TLS, `/api/*` на реплики, `/media/*` на SeaweedFS без переписывания пути, статика-заглушка, журнал доступа без токенов |
| `api-a`, `api-b` | 512 МБ | две реплики API, балансировка `least_conn`, активная проверка `/health/serving` (только слив, без PostgreSQL и Redis) |
| `worker`, `worker-default` | по 256 МБ | очереди писем и плановых задач (arq) |
| `worker-media` | 768 МБ | очередь файлов: обработка изображений Pillow (WebP, варианты, аватары) и удаление объектов; две задачи разом, бюджет декодирования 400 МБ ([runbook файлов](media.md)) |
| `postgres` | 2 ГБ | PostgreSQL 18, настройки из 4.16, архивация WAL в pgBackRest |
| `pgbackrest` | 256 МБ | расписание копий и проверка архивации ([runbook копий](backup-restore.md)) |
| `redis` | 384 МБ | Redis 8, AOF, пароль |
| `seaweedfs` | 768 МБ | S3 API: bucket `media` (файлы) и `pgbackrest` (копии БД); больше ничего наружу не торчит (ниже) |
| `mailpit` | 64 МБ | вместо почтового провайдера (его подключит S21) |

Одноразовые задачи: `s3-certs` (сертификат HTTPS-порта SeaweedFS для pgBackRest), `db-init` (роли и база), `migrate` (миграции). Buckets создаёт сам контейнер SeaweedFS при старте (`S3_BUCKETS`), поэтому отдельной задачи для них нет. Лимиты задают память (своп выключен) и общие четыре ядра (`cpuset` у всех контейнеров, по умолчанию `0-3`, как у VPS; на другой машине номера ядер меняет `STAND_CPUSET`). Все контейнеры стенда работают с `no-new-privileges`. Проверка: `make stand-stats` печатает потребление, лимиты, OOM-убийства и сумму лимитов (5,3 ГиБ из 8).

Секреты монтируются по необходимости (S6): ключ подписи токенов (`jwt_private_key`) только у `api-a` и `api-b`, пароль почтового сервера (`smtp_url`) только у `worker`; `worker-media`, где кодеки разбирают чужие файлы, и `worker-default` не получают ни того ни другого (у них ключи БД и S3). Переменная `*_FILE` без смонтированного файла роняет приложение при старте, поэтому секрет и переменная идут парой; расхождение ловит `scripts/check_compose_secrets.py` (в CI и руками).

### Почему SeaweedFS закрыт почти целиком

У `weed server` нет аутентификации ни у master, volume и filer, ни у gRPC-портов, а gRPC S3 (`18333`, `SeaweedS3IamCache.PutIdentity`) позволяет любому соседу по сети создать себе администратора S3: это воспроизведено на изолированном контейнере при проверке S4. Поэтому внутри контейнера всё, кроме S3, слушает только `127.0.0.1` (`-ip.bind`, `-s3.ip.bind`), порты Iceberg и Lance выключены (`-s3.port.iceberg=0`, `-s3.port.lance=0`), а в сеть `internal` выходят только S3 по HTTP (`8333`) и HTTPS (`8334`): `deploy/seaweedfs/entrypoint.sh` пробрасывает их `socat` с локальных `9000` и `9001`. Доступ к S3 защищён ключами. Проверяет это `tests_v2/stand/test_internal_network.py`: два порта открыты, остальные двенадцать закрыты. Тот же набор правил в `compose.dev.yml` (порт `8333` публикуется на `127.0.0.1`).

Сети: `edge` (Caddy и Mailpit: Docker публикует порты только у контейнеров сети с выходом наружу; воркеры шлют письма Mailpit по `internal`), `internal` (без выхода наружу: PostgreSQL, Redis, SeaweedFS и все остальные), `egress` (API и воркеры, как на VPS). Секреты читаются из файлов `deploy/secrets/*` (в git их нет); приложение берёт их через `<ИМЯ>_FILE`. `--force` у `scripts/init_prod_like.py` создаёт все секреты заново, после него стенд нужно сбросить: пароли ролей и ключ шифрования копий нельзя сменить под существующими томами.

## Проверки стенда

```bash
make stand-test          # 98 тестов через Caddy: TLS, заголовки, 404, SSE, WebSocket, presigned URL, загрузка и обработка файлов (S5, S6), журнал, закрытые порты
make smoke               # быстрый дымовой тест (его же запускает выкладка)
py -3 scripts/check_compose_secrets.py   # секреты разведены по сервисам: ключ токенов только у API, SMTP только у воркера почты
py -3 scripts/stand_browser_check.py   # то же настоящим браузером (headless Edge или Chrome)
```

Тесты стенда запускаются в контейнере `stand-tools`: он в сети стенда, ходит на тот же адрес `https://messunjerr.localhost`, что и браузер, и доверяет корневому сертификату из тома Caddy. Без запущенного стенда они пропускаются (кроме 16 офлайн-тестов подписи SigV4 и пробы нагрузки). Тесты загрузки файлов (`test_uploads.py`) работают с постоянными аккаунтами `stand-owner` и `stand-other`: первый прогон регистрирует их через настоящий API и письмо в Mailpit стенда, следующие только входят. Лимиты запросов действуют и на тесты (регистраций с одного адреса 5 в час, заявок на загрузку 60 в час на человека): при отказе тест падает с подсказкой, счётчики сбрасывает `make stand-reset-limits`.

## Выкладка без простоя и откат

```bash
make deploy TAG=v2       # собрать образ messunjerr-v2-prod:v2 и выкатить (без TAG берётся метка времени)
make rollback            # вернуть предыдущую выкладку
```

(`./dev.ps1 deploy v2`, `./dev.ps1 rollback`; скрипты `deploy/rollout.sh` и `deploy/smoke.sh` написаны на bash, на Windows `dev.ps1` берёт bash из Git.)

Порядок: образ → миграции отдельной задачей (`migrate`) → `api-a`, затем `api-b` по одной → воркеры → дымовой тест. Каждая реплика перед остановкой сливает трафик: `SHUTDOWN_DRAIN_SECONDS` (5 с) `/health/serving` и `/health/ready` отвечают `503`, Caddy по активной проверке `/health/serving` (раз в 2 с) снимает её с балансировки, потоки SSE заканчиваются событием `bye`, WebSocket закрываются кодом 1001 (клиенты переподключаются к соседней реплике), и только потом uvicorn перестаёт принимать соединения и дожидается текущих запросов (до 20 с). `/health/live` всё это время отвечает 200, поэтому Docker не считает реплику упавшей. Проверка Caddy (`/health/serving`) намеренно не смотрит на PostgreSQL и Redis: при общем сбое зависимости обе реплики остались бы в балансировке и отвечали бы ошибками сами (быстро), а не уходили бы разом, оставляя клиентов на пять секунд ожидания Caddy перед `503`. Полную готовность (`/health/ready`: PostgreSQL, Redis, миграции) проверяют скрипты выкладки и внешний мониторинг. Порядок для новой проверки такой же, как для любой ручки, которую опрашивает Caddy: сначала релиз с ручкой, потом Caddyfile, который её опрашивает (иначе старые реплики отвечают 404 и выпадают из балансировки), а откат ниже версии без ручки после смены Caddyfile невозможен.

Пока идёт выкладка, фоновая нагрузка (`tests_v2/stand/probe.py` в отдельном контейнере) гоняет запросы, один поток SSE и одно соединение WebSocket с переподключением. Итог печатается в конце:

```
http: запросов 19513, ошибок 0, статусы {'200': 19513}
http: версии, которые отвечали (build): {'s4a': 3883, 's4b': 9019}
sse: открыто 5, закончено сливом (bye) 4, оборвано 0
ws: открыто 2, закрыто кодом 1001 1, закрыто другим кодом 0, ошибок подключения 0
проба: неожиданных исключений 0
probe: ОШИБОК НЕТ
```

Итог чистый, только если открыты и SSE, и WebSocket (иначе нагрузка ничего не доказала), нет ошибок HTTP, оборванных потоков, ошибок подключения и неожиданных исключений. Выкладка считается успешной, только если итог чистый. Если сломалась миграция, реплики не трогаются. Если новая версия не стала готовой или не прошла дымовой тест, код возвращается на прошлый тег автоматически (при плохом образе пострадает одна реплика, вторая продолжает отвечать). Перед остановкой реплики скрипт проверяет, что соседняя готова (иначе выкладка отказывается стартовать: это был бы простой), а при откате этого не требует: откат нужен именно тогда, когда что-то уже сломано, и неготовые реплики он возвращает первыми. `--no-probe` отключает фоновую нагрузку.

**Миграции и готовность.** Миграции назад не откатываются: схема обязана быть совместимой с обоими версиями кода («расширить → мигрировать → сузить», 4.16). Когда `migrate` уже продвинул БД, а реплики ещё на старом коде, старый код видит в БД ревизию, которой не знает. Это значит «БД новее кода», а не поломку, поэтому `/health/ready` остаётся `200` с `migrations: ahead` (`head` — на последней ревизии, `behind` — известная, но не последняя: не готова, `unknown` — ревизию определить не удалось). Репетиция с настоящей новой ревизией (`make rehearse-migration`) собирает одноразовый образ с пустой миграцией, выкатывает его, откатывает на прежний код против БД «впереди», проверяет `ahead`, возвращает БД на прежнюю ревизию и удаляет образ; фоновая нагрузка считает ошибки клиентов в обеих выкладках.

**Откат через границу версий.** Compose описывает сервисы текущей версии, поэтому откат работает между образами с одним набором сервисов. Образ старее S5 не знает очереди `media`: `worker-media` на нём не запустится, и `rollback` на такой тег завершится ошибкой (сервисы `api-a`, `api-b`, `worker` и `worker-default` при этом вернутся). Сервис, которого нет в старом образе, перед откатом через такую границу останавливают вручную (`docker compose -p messunjerr-stand -f deploy/compose.yml stop worker-media`).

**Откат S6 на S5** границу не пересекает (набор сервисов тот же), данные совместимы: аватары остаются на месте, адреса те же. Нюанс: S5 не знает префикса `public/avatars/` и формата `variants` S6, поэтому аватары, удалённые или замещённые за время работы S5, оставят файлы в хранилище; при возврате на S6 суточная сверка `sweep_orphan_objects` их найдёт (строки `deleted` уже закрыты) и уберёт. Лимит памяти `worker-media` вернётся к 256 МБ только вместе с Compose прошлой версии.

**Откат через разведение секретов (S6, по итогам ревью).** Первая сборка S6 требовала ключ подписи токенов у любого процесса, а `compose.yml` после ревью даёт его только API (воркеры получают лишь то, что им нужно). Воркеры этой сборки с новым Compose не запустятся: откат на неё нужен вместе с `compose.yml` её релиза (в S21 CD берёт Compose из тега). Сборка после ревью ключа у воркеров не требует и работает с обоими Compose. Столбец `processing_attempts` (миграция 0005) прежнему коду не мешает: он его не знает, а значение по умолчанию 0.

**Состояние и прерванная выкладка.** Скрипт хранит в `deploy/.stand/` теги `current_tag`, `previous_tag` и `pending` (пока выкладка идёт). Выкладка того же тега, что уже выкачен, ничего не делает: тег образа неизменяем. Если скрипт прервали (Ctrl+C, перезагрузка), `pending` остаётся, реплики могут работать из разных сборок, а новая выкладка другого тега отказывается стартовать. Состояние покажет `bash deploy/rollout.sh status`. Завершить прерванную выкладку: `make deploy TAG=<тот же тег>`; отменить: `make rollback` (вернёт то, что было до неё).

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `bind: address already in use` на 80 или 443 | порт занят другой программой (IIS, другой Caddy, Docker-проект): остановить её или стенд |
| браузер ругается на сертификат | не выдано доверие корневому сертификату (раздел выше) или том `caddy_data` пересоздан |
| `messunjerr.localhost` не открывается | добавить `127.0.0.1 messunjerr.localhost` в hosts; проверить, что стенд поднят (`make ps-prod-like`) |
| `Container ... is unhealthy` при выкладке | `make logs-prod-like s=api-a`; скрипт сам вернёт прошлую версию |
| `не завершена выкладка A → B` или «прервано посреди выкладки» | `bash deploy/rollout.sh status`; завершить: `make deploy TAG=B`; отменить: `make rollback` (раздел про состояние выше) |
| `не готова, останавливать нельзя` | соседняя реплика нездорова, выкладка отказывается создавать простой: починить её (`make logs-prod-like s=api-b`) или откатиться (`make rollback` возвращает неготовые реплики первыми) |
| `make reset-prod-like` не удаляет тома | в проекте остались контейнеры профилей `drill` и `tools` (учение, тесты); цель использует `--profile '*'`, при ручном `docker compose down -v` добавьте его |
| стенд завис или не хватает места | `docker system df`; Docker Desktop хранит образы и тома на диске WSL, на C: должно быть свободное место |
| после `--force` у секретов ошибки входа в PostgreSQL | пароли в томе старые: `make reset-prod-like`, затем `make up-prod-like` |

## Что меняется на сервере (S21)

Тот же `compose.yml` и тот же Caddyfile; отличия: домен и `TLS_MODE=tls_auto` (Let's Encrypt, `ACME_EMAIL`), `HSTS_MAX_AGE` по умолчанию (год), SMTP провайдера вместо Mailpit, образ из GHCR (`pull` вместо `build`), `APP_ENV=prod` (без документации и тестовых ручек), копии pgBackRest в S3 российского провайдера, секреты в каталоге с правами `0700` у root, без `SPIKE_ENDPOINTS_ENABLED`.

Известное ограничение стенда, которое снимает S21: `FORWARDED_ALLOW_IPS` равен `*`, то есть заголовкам `X-Forwarded-*` верят от любого соседа по сети `internal` (подделать IP клиента мог бы только скомпрометированный контейнер стенда, снаружи до API можно добраться лишь через Caddy, который эти заголовки пересоздаёт). На сервере Caddy получает отдельную сеть `proxy` с закреплённым адресом, и список доверенных адресов сужается до него.
