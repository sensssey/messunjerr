# Потоки, асинхронность и RPS: теория и замеры на этом проекте

Этот документ отвечает на три вопроса:

1. как на самом деле устроены многопоточность и асинхронность в Python (и что не так с фразой «в питоне нет асинхронности, потому что нет многопоточности»);
2. что было бы, если писать этот бэкенд на Go, при условии что обе реализации качественные;
3. как выжимать много RPS из FastAPI.

Все числа в разделе «Замеры» получены **на этом репозитории** 2026-10-04: ноутбук AMD Ryzen 7 7840H (8 ядер / 16 потоков), Docker Desktop (WSL2, 16 ГБ на VM), Python 3.12.8, uvicorn + uvloop, PostgreSQL 16 в соседнем контейнере. Генератор нагрузки работал на той же машине, то есть отъедал CPU у сервера: числа консервативные и «бытовые», не лабораторные. На VPS с одним слабым ядром делите примерно на 2–4.

---

## 1. Теория: процессы, потоки, GIL

**Процесс** — отдельная программа со своей памятью. **Поток** — параллельная ветка исполнения внутри процесса, память общая. Планирует и то и другое ОС, вытесняя в любой момент.

**GIL** (Global Interpreter Lock) — замок в CPython: исполнять **байткод Python** в каждый момент может только один поток процесса. Отсюда и миф. Но у GIL три важные оговорки:

1. **GIL отпускается на время ожидания ввода-вывода.** Пока поток ждёт сокет, диск или `time.sleep`, другие потоки работают. Поэтому потоки в Python отлично годятся для I/O и бесполезны только для чистопитоновых вычислений.
2. **GIL отпускают C-расширения.** `bcrypt`, значительная часть `Pillow`, `numpy`, сжатие, криптография — всё это внутри C-кода работает параллельно в обычных потоках. Это не теория: в замере логина ниже один процесс Python нагрузил **~14,5 ядер** (CPU контейнера 1450%), потому что bcrypt-хэширование шло в пуле потоков и GIL ему не мешал.
3. **GIL — на процесс, а не на интерпретатор вообще.** Два процесса = два GIL. Процессы масштабируют CPU-нагрузку линейно, что тоже видно в замерах.

С Python 3.13 существует официальная **free-threaded сборка** (без GIL): это отдельный вариант сборки, не дефолт, с накладными расходами 1–8% в однопотоке и неполной совместимостью C-расширений. Для веб-бэкенда она пока не нужна: процессы решают ту же задачу проще.

## 2. Теория: асинхронность

Асинхронность — это **не потоки**. Это кооперативная многозадачность в **одном** потоке:

- **event loop** крутится в одном потоке и спрашивает у ОС (epoll/kqueue/IOCP): «на каких из моих тысяч сокетов появились данные?»;
- **корутина** (`async def`) исполняется до ближайшего `await` и в этой точке добровольно отдаёт управление;
- пока одна корутина ждёт БД, loop исполняет сотни других.

Потоки для конкурентности здесь не нужны вовсе — конкурентность достигается тем, что никто не ждёт «вхолостую». Многопоточность и асинхронность — независимые механизмы, поэтому «нет многопоточности → нет асинхронности» — это соединение двух несвязанных вещей. В замере ниже один процесс с **пятью потоками ОС** обслужил 5000 одновременных запросов.

Цена вопроса — **кооперативность**: если корутина заблокирует поток (синхронный драйвер БД, `requests`, `time.sleep`, тяжёлая картинка), встанет весь loop и все его клиенты. Это главный способ «сломать» FastAPI, см. замер.

### Что чем масштабировать

| Тип нагрузки | Правильный инструмент | Почему |
|---|---|---|
| Много одновременных ожиданий (БД, HTTP, сокеты, WebSocket) | `async` / event loop | один поток держит тысячи ожиданий |
| Блокирующая библиотека без async-версии | пул потоков (`def`-эндпоинт, `run_in_threadpool`) | GIL отпускается на I/O |
| CPU-работа в C-расширении (bcrypt, Pillow, numpy) | тоже пул потоков | C-код отпускает GIL |
| CPU-работа на чистом Python | **процессы** (workers / реплики / очередь задач) | у каждого процесса свой GIL |

Как это разложено в нашем коде: эндпоинты асинхронные, БД через asyncpg (await), а bcrypt и Pillow уходят в пул потоков (`run_in_threadpool` в [auth.py](../backend/src/auth/auth.py) и [profile/routes.py](../backend/src/profile/routes.py)).

### FastAPI: `async def` против `def`

- `async def` — исполняется прямо в event loop. Внутри можно только await'ить; блокирующий вызов запрещён.
- `def` — FastAPI сам уводит его в пул потоков (по умолчанию ~40 потоков). Медленнее на запрос и ограничено размером пула, зато блокирующий код безопасен.

## 3. Замеры

### 3.1. Миф «асинхронности нет»: ожидание I/O, один процесс

Эндпоинт ждёт 0,1 с (имитация медленного I/O). Один процесс uvicorn.

| Вариант | Параллельных запросов | Время | Потоков ОС |
|---|---:|---:|---:|
| `async def` + `await asyncio.sleep(0.1)` | 100 | **0,16 с** | 5 |
| `async def` + `await asyncio.sleep(0.1)` | 1000 | **0,52 с** | 5 |
| `async def` + `await asyncio.sleep(0.1)` | 5000 | **3,48 с** | 5 |
| `def` + `time.sleep(0.1)` (пул потоков) | 100 | 0,42 с | 45 |
| `def` + `time.sleep(0.1)` (пул потоков) | 1000 | 2,87 с | 45 |
| `async def` + `time.sleep(0.1)` — **ошибка, блокирует loop** | 20 | **2,03 с** (всё по очереди) | 45 |

Последовательно 1000 запросов по 0,1 с заняли бы 100 секунд; асинхронно — полсекунды на пяти потоках ОС. А одна строчка блокирующего кода в `async def` превращает сервер обратно в очередь.

### 3.2. GIL на CPU-нагрузке и выход через процессы

Каждый запрос жжёт 50 мс процессорного времени (потолок одного ядра — 20 запр/с). 40 запросов параллельно.

| Конфигурация | Запр/с | Комментарий |
|---|---:|---|
| 1 процесс, CPU в event loop | 19,6 | ровно одно ядро — GIL |
| 1 процесс, CPU в пуле потоков | 19,5 | потоки не помогли: чистый Python |
| `uvicorn --workers 4` (один порт) | 33,8 | накат соединений лёг неровно: [23, 15, 1, 1] |
| `uvicorn --workers 8` (один порт) | 37,0 | та же беда: [21, 17, 1, 1] |
| 4 процесса + честный балансировщик | **77,1** | ×3,9 — линейно |
| 8 процессов + честный балансировщик | **144,9** | ×7,2 — линейно |

Два вывода. Процессы полностью обходят GIL. И: встроенный `--workers` делит соединения между воркерами плохо, когда клиенты приходят пачкой и живут долго (accept разбирает кто успел); внешний балансировщик (Caddy/nginx) раздаёт равномерно — на длинной равномерной нагрузке разница сглаживается (см. 3.4, строка D).

### 3.3. Реальное приложение: RPS по эндпоинтам

Код этого репозитория как есть: 1 процесс uvicorn, настоящий PostgreSQL, 64 одновременных keep-alive соединения, 10 секунд на тест.

| Эндпоинт | Запр/с | p50 | p95 | CPU API / CPU PG |
|---|---:|---:|---:|---|
| `GET /ping` (без БД, базовая линия) | **4444** | 14 мс | 18 мс | — |
| `GET /health` (1 SELECT) | **514** | 113 мс | 161 мс | 96% / 23% |
| `GET /auth/users/me` (JWT + 2 SELECT) | **319** | 185 мс | 204 мс | 100% / 29% |
| `GET /posts/?limit=20` (JWT + 2 SELECT + сериализация 20 строк) | **222** | 274 мс | 340 мс | 98% / 18% |
| `POST /posts/` (INSERT + COMMIT) | **196** | 232 мс | 581 мс | — |
| `POST /auth/token` (вход: bcrypt) | **38** | 868 мс | 982 мс | **1450%** / 2% |

Как читать:

- Узкое место везде — **одно ядро Python** (CPU API ~100%), а не Postgres (≤30%) и не фреймворк как таковой. Чистое время обслуживания `GET /posts/` — ~4,5 мс; большие p50 — это **очередь**: 64 соединения долбят процесс, который успевает 222 в секунду. При реальной нагрузке в десятки запр/с задержки будут единицы миллисекунд.
- Вход — 38 запр/с и ~0,9 с на запрос **специально**: bcrypt обязан быть дорогим, это защита паролей от перебора. CPU 1450% — тот самый пример параллельных потоков в Python (bcrypt отпускает GIL). Логин не масштабируют — его ограничивают (rate limit).
- Разница 4444 → 514 показывает цену одного похода в БД + валидации; 514 → 222 — цену JWT-проверки, второго SELECT и сериализации 20 объектов.

### 3.4. Масштабирование реального эндпоинта

`GET /posts/?limit=20`, те же 64 соединения:

| Конфигурация | Запр/с | p50 | Ускорение |
|---|---:|---:|---:|
| 1 процесс | 216 | 281 мс | ×1,0 |
| 2 процесса за балансировщиком | 415 | 144 мс | ×1,9 |
| 4 процесса за балансировщиком | 757 | 78 мс | ×3,5 |
| 8 процессов за балансировщиком | **1337** | 46 мс | ×6,2 |
| `uvicorn --workers 4` (один порт) | 768 | 78 мс | ×3,6 |

На длинной нагрузке `--workers 4` ≈ 4 реплики. Рост чуть ниже линейного: ядра делятся с Postgres и самим генератором нагрузки.

### 3.5. WebSocket: сколько держит один процесс

Один процесс uvicorn, клиенты подключаются и молчат (как вкладки чата), затем сервер рассылает одно сообщение всем.

| Соединений | RSS процесса | Память на соединение | Рассылка всем |
|---:|---:|---:|---:|
| 1 000 | 171 МБ | ~120 КБ | 68 мс |
| 5 000 | 732 МБ | ~114 КБ | 279 мс |
| 10 000 | 1,6 ГБ | ~89 КБ | 872 мс |

Потоков ОС — всё те же 5. Десять тысяч одновременных подключений на одном процессе — при том что чату «для своих» нужны десятки. Ограничители дальше: память (~0,1 МБ на соединение) и линейный рост времени рассылки; при нескольких процессах понадобится pub/sub (Redis), потому что соединения разных воркеров друг друга не видят.

## 4. FastAPI против Go (оба бэкенда качественные)

Важно: Go здесь **не замерялся** — сравнение качественное, по устройству рантаймов и общеизвестным порядкам величин. Точные кратности зависят от кода и железа.

### Как устроена конкурентность

| | Python / FastAPI | Go |
|---|---|---|
| Модель | event loop в одном потоке + пул потоков + процессы | **горутины**: M:N-планировщик раскладывает миллионы лёгких задач по всем ядрам |
| CPU-параллелизм | только процессами (GIL) | из коробки, в одном процессе |
| Память на соединение | ~90–120 КБ (наш замер) | горутина стартует с ~2–8 КБ стека |
| «Цветные» функции | есть: мир делится на sync/async, блокирующий вызов в loop — авария | нет: любой код можно звать откуда угодно, планировщик сам разрулит |
| Хвосты задержек | джиттер от очереди к GIL и пула потоков | ровнее: GC с паузами меньше миллисекунды, нет GIL |

### Порядки величин

- На тривиальных хендлерах (JSON без БД) качественный Go-сервер на этом же железе показал бы не тысячи, а **десятки–сотни тысяч** запр/с — на порядок больше нашей базовой линии в 4444.
- На эндпоинтах с БД разница сжимается до **единиц раз**: Python тратит заметно больше CPU на запрос (валидация, сериализация, интерпретация), поэтому для тех же RPS ему нужно больше ядер/реплик, но упор всё равно рано или поздно в Postgres и диски.
- На WebSocket Go держит сотни тысяч соединений на процесс против наших десятков тысяч — другой порядок, который вашей соцсети не потребуется.

### Что это значит на практике

| Критерий | FastAPI | Go |
|---|---|---|
| Скорость разработки фич | валидация (Pydantic), OpenAPI/Swagger, DI — из коробки | руками или библиотеками (chi/echo + validator + swag); больше шаблонного кода |
| Потолок RPS на ядро | ниже | заметно выше |
| Деплой | интерпретатор + зависимости (у нас Docker-образ 381 МБ) | один статический бинарник, десятки МБ, мгновенный старт |
| Память под нагрузкой | больше | меньше |
| Ошибки конкурентности | asyncio в одном потоке — data race почти исключены | потоки настоящие: гонки возможны, есть `-race`-детектор |
| Экосистема для ML/скриптов/ботов | богатейшая | скромнее |

**Вывод для этого проекта.** Оба стека справятся с нагрузкой «друзья + все желающие» с огромным запасом; узкое место у вас — одна машина с Postgres, а не язык. FastAPI выигрывает там, где сейчас ваша реальная цель: быстро наращивать фичи (дружба, стена, чат) и показывать аккуратный API. Go выигрывает, когда нужен максимум RPS на ядро, минимальная память, сотни тысяч соединений — или когда хочется выучить язык. Разумный компромисс для портфолио: ядро на FastAPI + один отдельный сервис на Go (например, WebSocket-шлюз или ресайзер картинок) — так вы покажете оба стека, не переписывая всё.

## 5. Как выжимать RPS из FastAPI

По убыванию эффекта. Пункты с ✅ в этом репозитории уже сделаны, с ⬜ — следующие шаги.

**Архитектура процесса**
1. ⬜ **Процессы = ядра.** Один uvicorn использует одно ядро на Python-код. `--workers N` или N реплик контейнера за Caddy/nginx — наш замер дал ×6,2 на 8 процессах. На одноядерном VPS этот пункт бесплатного прироста не даст.
2. ✅ **uvloop + httptools.** Уже стоят и подхватываются uvicorn автоматически (это и мерили).
3. ✅ **Никогда не блокировать event loop.** Один `time.sleep`/`requests`/синхронный драйвер в `async def` — и сервер встал (замер 3.1, последняя строка). Всё блокирующее — в `def`-эндпоинты или `run_in_threadpool` (у нас bcrypt и Pillow), тяжёлый чистый Python — в очередь задач.
4. ✅ **bcrypt дорогой по замыслу.** Не ускорять, а ограничивать частоту логина (rate limit в Caddy или slowapi) и жить с JWT между логинами.

**База данных**
5. ✅ **Асинхронный драйвер + пул соединений** (asyncpg). Следить, чтобы `pool_size × воркеры` не упёрся в `max_connections` Postgres; при большом числе реплик — PgBouncer.
6. ✅ **Индексы под реальные запросы** (у нас `posts.user_id`) и `EXPLAIN ANALYZE` для медленных.
7. ✅ **Не тянуть лишнего.** Раньше каждый авторизованный запрос вытаскивал из БД аватар целиком (`lazy="selectin"` на User) — убрали; это классический скрытый N+1. Большие поля (наш `avatars.file_data`) не должны ездить в каждом SELECT.
8. ⬜ **Файлы — не в БД.** Аватары/фото в объектное хранилище или на диск за Caddy; БД хранит путь. Плюс `Cache-Control`/`ETag`, чтобы браузер не скачивал аватар заново.
9. ⬜ **Пагинация курсором** по `(created_at, id)` для лент: `OFFSET` на больших страницах деградирует линейно.

**HTTP-слой**
10. ⬜ **Кэш горячего чтения в Redis** (профили, ленты, счётчики) с коротким TTL — раз Redis всё равно в планах. Самый дешёвый способ умножить RPS чтения на порядок.
11. ⬜ **Сжатие и TLS — на Caddy,** не в Python. Keep-alive обязателен (наш генератор держал соединения — иначе цифры были бы в разы хуже из-за рукопожатий).
12. ⬜ **Лимиты и таймауты:** `--limit-concurrency` у uvicorn, таймауты у Caddy — защищают p99 и не дают одному клиенту занять всё.
13. ✅ **`response_model` без лишних полей** — сериализация 20 постов уже стоила нам разницы 514 → 222 запр/с; отдавать мегабайтные ответы — убивать RPS.

**Фоновая работа и реалтайм**
14. ⬜ **Тяжёлое — в очередь.** Ресайз фото, рассылки, пересчёт лент — через Celery/arq/taskiq, API отвечает 202 сразу. Celery классический — синхронный prefork: это нормально для таких задач (они и не async), но писать таски придётся синхронными; нативно-асинхронные альтернативы — arq и taskiq.
15. ⬜ **WebSocket на несколько воркеров** требует pub/sub (Redis) — соединения в разных процессах иначе не увидят сообщения друг друга. На одном процессе хватит и `ConnectionManager` из документации; авторизовать соединение один раз при подключении, а не на каждое сообщение.

**Дисциплина**
16. ⬜ **Сначала мерить, потом оптимизировать:** py-spy на живом процессе, встроенный OpenTelemetry (FastAPI ≥ 0.142), нагрузочный прогон перед каждым «ускорением». Оптимизации без профиля чаще всего чинят не то.

### Грубая арифметика для планирования

Соцсеть — это в основном чтение. Если каждый активный пользователь делает запрос раз в 3–5 секунд (агрессивно), то 1000 человек онлайн ≈ 200–350 запр/с. Это **один процесс** нашего нынешнего кода; 4 реплики дают четырёхкратный запас, Redis-кэш — ещё порядок. Потолок этого стека на нормальном сервере — тысячи RPS и десятки тысяч WebSocket-соединений; упрётесь вы сначала в Postgres и в деньги на хостинг, а не в FastAPI.
